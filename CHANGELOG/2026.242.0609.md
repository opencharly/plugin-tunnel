# 2026.242.0609 — fix: stamp the root manifest at the schema this repo's CI charly supports

## Summary

**One commit, one line:** corrects the root manifest's schema stamp from `2026.240.1943` to
`2026.232.0520`.

The root `charly.yml` itself landed earlier (opencharly/plugin-tunnel#2) and is already on
`main` — this PR does **not** add it. That earlier commit stamped the current schema HEAD
`2026.240.1943`, but this repo's `deploy.yml` pins charly `v2026.238.1242`, whose maximum
supported schema is `2026.232.0520`. So the `candy` workflow began failing on `main` with:

```
config schema 2026.240.1943 is newer than this charly supports (max 2026.232.0520)
```

This stamps `2026.232.0520` — the value the peer candy repos already carry, and the one this
repo's pinned charly accepts. Nothing under `candy/` is touched; the schema requirement
applies to the project **root** manifest only.

Refs opencharly/charly#459.

## How tested

Against a binary built from **this repo's own pinned charly tag** (`v2026.238.1242`), on
this PR's branch — using a newer local build is precisely what caused the bad stamp.

**Accepted at the corrected stamp:**

```
$ charly box validate
exit=0
```

(no diagnostics; the command exits cleanly)

**And the gate still bites** — quiet acceptance would be worthless. Changing this repo's own
`- verb:tunnel` provider entry in `candy/plugin-tunnel/charly.yml` to `- notaclass:tunnel`:

```
charly: error: command "validate": 2 validation errors:

  candy "plugin-tunnel": CUE schema: .../candy/plugin-tunnel/charly.yml:
  candy "plugin-tunnel": 2 errors in empty disjunction:
  plugin: field not allowed:
```

So the repo keeps the working gate that #2 was for, and its `candy` workflow goes green again.
