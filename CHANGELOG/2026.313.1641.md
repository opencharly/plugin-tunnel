# 2026.313.1641 — feat(schema)!: import the contract's tunnel defs instead of restating them

## Summary

`candy/plugin-tunnel/schema/tunnel.cue` restated the contract's two tunnel wire definitions — `#TunnelConfig`
and `#TunnelPort` — as local twins, and the generated `params` package carried its own `TunnelConfig` /
`TunnelPort` structs beside them. One name, one home: the contract module (`github.com/opencharly/spec/schema`)
owns those shapes (the resolved wire carrier that the pod-lifecycle plugins marshal over this verb's
`{method,config}` envelope and that `sdk/deploykit`'s quadlet emitter consumes), and the census this PR
retires counted both sites — opencharly/opencharly#950 is the mechanism, opencharly/opencharly#945 the count.

The schema now imports `schema.#TunnelConfig` and declares only its own `#TunnelInput`. The generation leg is
unchanged and in-process: `spec/schemaparams.Generate` composes the source as ONE offline CUE module instance
(no network, no module cache, no `cue.mod`, no `cue` CLI) and emits the field through the Go package that owns
the shapes, so `params.TunnelInput.Config` is `spec.TunnelConfig`. The exec leg moves to the contract types;
their `int` fields replace the gengotypes `int64` rendering (`strconv.Itoa` for `FormatInt`).

`spec` and `sdk` are bumped **together** — v0.2026313.1428 and v0.2026313.513. That lockstep is measured, not
stylistic: the older sdk's `vmshared/spec_aliases.go` re-exports spec types the newer spec dropped, and the
sdk's own helper packages import it, so a spec-only bump does not build.
